# Growing the sequential test set from annotator imports

**Status**: implemented (2026-08-14)
**Date**: 2026-08-14
**Scope**: the sequential dataset (`sequential_test`); split assignment for annotator imports

Successor to the deferred "Growing the test set from annotator data" item in
[2026-08-13-annotator-export-sequential-import-design.md](2026-08-13-annotator-export-sequential-import-design.md),
whose §4 ("Splits: train and val only") this design supersedes.

## Goal

Let annotator imports assign sequences to **all three splits** — automatic 80/10/10 —
while keeping models comparable across dataset releases: a model trained and evaluated
on an earlier release must remain comparable with a model trained on a later one.

Comparability here means **append-only growth**: every release's `sequential_test` is a
strict, byte-identical superset of the previous release's. An old model is re-evaluated
on the grown test set (or on the frozen old subset inside it); previously published
numbers are not kept valid as-is. That was the explicit choice — the lighter of the two
comparability contracts.

## Non-goals

- Append-only stability for the detector's `yolo_test`. Its WF half is naturally
  append-only (one global seeded RNG over an append-only registry), but its FP half
  re-rolls whenever the test FP pool grows (`round_robin_sample` shuffles a
  different-length list). Accepted: model comparison across releases is a
  temporal-model concern; the detector keeps today's behaviour.
- Cross-pool recurring-object matching (historical ↔ annotator), still the accepted
  residual risk of the import design.
- Same-fire matching against the historical pool. §6 guards annotator smoke against
  annotator smoke only.
- Growing test with *historical* data, or retroactively re-splitting anything.

## Background: why test is frozen shut today

The import design locked test out in three deliberate layers, all of which this design
touches:

- `assign_new_split` (`src/pyro_dataset/annotator/recurring.py`) draws from
  `SPLIT_TARGETS = {"train": 0.9, "val": 0.1}` — test is never a candidate.
- `assignments_from_splits` (`src/pyro_dataset/ingest.py`) raises on any pre-assigned
  `test` split, "where it cannot be bypassed".
- The import spec makes "annotator sequences never receive `split: test`" invariant #2.

The lock exists because the built test set is a **selection recomputed on every
build**, not a copy of the test split. `build_sequential_dataset.py` sets
`quota = n_wf` per split and picks FP negatives by two-stage selection — union-find
atoms, then KMeans with `k = quota` over DINOv2 embeddings of the whole test FP pool
(705 sequences for 151 slots today). One new WF test sequence raises the quota, changes
`k`, and KMeans re-clusters all 705 candidates: the historical negatives are silently
re-selected, not extended. New FP test sequences re-roll it through the pool and the
embeddings. The seed does not help — same seed, different `k` or different input
matrix, different output — and the two-stage selection is not even known to be
bit-reproducible across identical runs (float32 BLAS non-determinism, noted in the
import spec and never verified).

Test has therefore been stable **by DVC caching, not by design**: no dep of the stage
has changed since the last re-roll. This design replaces that accident with recorded
state.

## Design

### 0. State boundary: a lockfile and a manual freeze command

The import design established the principle: a DVC stage must be a pure function of its
declared deps, so accumulated state lives in git-committed files written by manual
commands (the plan, the ledger). The frozen test selection is accumulated state of
exactly the same kind, and gets the same treatment.

Two alternatives were rejected:

- **The build stage owns the lockfile.** As a declared `out` it is regenerated by
  `dvc repro`, destroying the pinning; as an undeclared side-write the stage lies to
  DVC and caching breaks. This is the trap the plan/ledger split exists to avoid.
- **A prefix-stable selection algorithm instead of a lockfile.** KMeans cannot be made
  prefix-stable; a custom greedy scheme would change today's test once (breaking
  comparability at the transition it exists to protect), and correctness would rest on
  an algorithmic invariant instead of recorded state.

So: **`data/raw/sequential_test_lock.json`** — an ordered, append-only list of FP
folder names, exactly the FP half of the built `sequential_test`:

```json
{"folders": ["pyronear_marguerite-282_212_2024-01-26T11-58-07", "..."]}
```

Small, diffable, **git-committed** at the `data/raw/` root — it cannot live inside
`data/raw/fp/`, which is a single DVC-tracked object (`fp.dvc`) whose gitignore would
swallow it and whose directory hash every freeze would churn. The git-tracked homes for
accumulated state are the `data/raw/` root and `data/raw/pyro-annotator/` (the ledger
and plan); the lockfile joins them, committed together with the DVC pointer of the
registries it froze against. A test-set change is a reviewable diff of pure additions.
Order is append order and is never changed — the file is history.

### 1. Opening the splits: 80/10/10, automatic

`SPLIT_TARGETS` in `recurring.py` becomes `{"train": 0.8, "val": 0.1, "test": 0.1}`.
`assign_new_split` needs no logic change: test is simply a third candidate for newly
minted recurring objects and new smoke groups. Existing ledger entries and plan entries
keep their recorded splits — split assignment happens only at mint, and the ledger is
authoritative, so nothing already imported can move.

`assignments_from_splits` drops its test refusal: a `"test"` split in `splits.json`
flows through to the registry like any other. The rule it enforced is repealed, not
relocated.

`apply_force_train` already generalises: it refuses to move any object with staged
sequences outside train, which now covers test. Forcing a test-split object to train
remains possible only while it has ingested nothing.

**Catch-up effect, accepted.** The greedy deficit assignment seeds its counts from the
ledger and the plan, which today stand at roughly 90/10/0 across ~161 counted entries.
Test's deficit therefore dominates until the ratio catches up: the first ~15–20 new
assignments after this change land almost entirely in test. Self-correcting, and
aligned with the goal — the whole point is to start growing test — so it is accepted
rather than special-cased with a "count only post-change entries" epoch.

### 2. The freeze command

`scripts/freeze_test_selection.py` — manual, never a stage, for the same reason as
`plan_annotator_import.py`: it reads and rewrites accumulated state.

```
uv run python scripts/freeze_test_selection.py [--dry-run]
```

| flag | default | |
|---|---|---|
| `--wf-registry` | `data/raw/wildfire/registry.json` | quota source |
| `--fp-registry` | `data/raw/fp/registry.json` | pool + pins |
| `--fp-data-dir` | `data/raw/fp/data` | existence checks |
| `--embeddings-dir` | `data/interim/fp_sequence_embeddings` | test embeddings for new slots |
| `--lockfile` | `data/raw/sequential_test_lock.json` | |
| `--bootstrap-from` | `data/processed/sequential_test` | seed source when no lockfile exists (§4) |
| `--nms-iou` / `--match-iou` / `--random-seed` | `0.3` / `0.7` / `0` | passed to `two_stage_select`, matching the build's defaults |

Each run:

1. **Quota** = number of `split: test` entries in the wildfire registry. The registry
   count, not the on-disk count: the registry is the source of truth for membership,
   and a missing folder is an error to surface (step 6), not a number to quietly shrink
   around.
2. **Load the lockfile.** Its entries are never removed and never reordered. If it
   already exceeds the quota — impossible through this command, so it means a hand
   edit or registry surgery — hard error, never truncate.
3. **Pin annotator test FPs**: registry entries with `source: pyro-annotator` and
   `split: test` not yet in the lockfile are appended in registry order (which is plan
   order — deterministic), **up to the quota** (§5).
4. **Fill remaining slots** by the existing `two_stage_select` over the test FP pool
   minus lockfile folders, with `quota = remaining slots`, appending the picks. The
   KMeans float non-determinism now affects only *which new negatives get frozen*, once,
   at freeze time — never what is already frozen.
5. **Validate**: every lockfile folder (old and new) is a registered `split: test` FP
   sequence and exists on disk. Error otherwise — a frozen test that cannot be
   materialised exactly is a comparability bug.
6. **Write** the lockfile (skipped under `--dry-run`), reporting what was appended and
   from where (pins vs. clustering).

Idempotent: a rerun with nothing new writes an identical file. An import that adds no
test WF sequences opens no slots, so freeze is a no-op (annotator test FPs beyond the
quota wait in the pool, §5).

### 3. Build changes

`build_sequential_dataset.py` gains `--test-lockfile` (default
`data/raw/sequential_test_lock.json`). For the test split it performs **no
selection**: the FP folders are the lockfile's, verbatim. It errors — not warns — when:

- the lockfile is missing, or its length ≠ quota
  (`"lockfile has 151 folders, quota is 160 — run freeze_test_selection.py"`);
- a lockfile folder is not a registered `split: test` FP sequence;
- a lockfile folder is missing on disk (the WF side keeps its warn-and-skip behaviour;
  the frozen FP side must materialise exactly or the guarantee is void).

Train and val keep today's per-build behaviour: annotator pinning plus fresh two-stage
selection, free to re-roll — comparability only binds test.

`dvc.yaml`: the lockfile joins the stage's deps;
`data/interim/fp_sequence_embeddings/test` leaves them, since the build no longer reads
test embeddings — only the manual freeze command does. `compute_fp_embeddings` still
produces them (an out consumed manually is fine — `materialise_annotator_sequences`
set the precedent). Test embedding churn therefore no longer rebuilds
`sequential_test`; only the lockfile and the registries do.

A pleasant consequence: building the test split becomes deterministic copying, which
retroactively settles the build-twice reproducibility question for test — the one the
import spec deferred alongside this work.

### 4. Bootstrap: the transition must not re-roll test

The first freeze run finds no lockfile. It must **not** recompute the selection — that
would trust KMeans to reproduce bit-identically what shipped, which is exactly the
assumption this design retires. Instead it seeds the lockfile from the folder names
under `<--bootstrap-from>/test/fp/` (the built dataset the current models were
evaluated on), validates them against the registry as in §2 step 5, and writes. If
neither a lockfile nor a built test set exists, it errors and says to `dvc pull` /
`dvc repro` first.

Run once, commit. From then on the lockfile exists in git and bootstrap never triggers
again.

### 5. Overflow rule

Smoke and FP splits are drawn independently, so an import can register more annotator
test FPs than its test smoke opened slots for (quota grows by the smoke count; pins
grow by the FP count; the two only match in expectation). Rule: pin **up to** the
available slots, in registry order; the surplus stays in the pool as ordinary
candidates — eligible for pinning at a later freeze when new smoke opens slots, and
meanwhile eligible for two-stage selection like anything else. Nothing is dropped, only
deferred; the 50/50 balance and the append-only property both hold.

### 6. Same-fire guard for smoke

The import design accepted that two alerts of one fire can straddle train and val
(observed in the reference export: `sdis-40_laluque-02_61`, two folders 147 minutes
apart, one in each). With test open, the same accident straddles train and *test*,
which inflates evaluation rather than merely being untidy. Minimal guard, at plan time:

- New smoke alerts on the same `(camera, azimuth)` whose timestamps sit within
  `--same-fire-window` (default 12 h) of each other — chained transitively — form one
  group, drawing **one split** for the group.
- The chain also matches against previously planned smoke folders (camera, azimuth and
  timestamp parsed from the folder name), inheriting the recorded split — so a later
  re-pull importing more alerts of an already-imported fire cannot re-roll it into
  another split.

The asymmetry justifying the generous window: a false merge costs nothing (two distinct
fires share a split), a false split leaks. Matching against the historical pool stays
out of scope, consistent with the import design's accepted residual risks.

| file | change | why |
|---|---|---|
| `src/pyro_dataset/annotator/recurring.py` | `SPLIT_TARGETS` gains `test: 0.1` (targets become 80/10/10) | §1 |
| `src/pyro_dataset/ingest.py` | `assignments_from_splits` stops refusing `test` | §1 |
| `scripts/plan_annotator_import.py` | same-fire grouping for new smoke (§6); `split_counts` seeds and reports include test; "Next:" output gains the freeze step | §1, §6, §8 |
| `scripts/build_sequential_dataset.py` | test split reads the lockfile, no selection; hard errors on stale/invalid lockfile | §3 |
| `dvc.yaml` | lockfile added to `build_sequential_dataset` deps; `fp_sequence_embeddings/test` removed from them | §3 |
| `scripts/freeze_test_selection.py` | **new** manual command | §2, §4 |

### 8. Workflow

The import gains one step (freeze) between registration and the rebuild:

```bash
dvc pull data/raw/pyro-annotator/export                      # full re-pull, 2.2 GB
uv run python scripts/plan_annotator_import.py               # --dry-run first
dvc repro materialise_annotator_sequences
uv run python scripts/add_data.py --src data/interim/pyro-annotator/sequences/wildfire \
  --type wildfire --splits-from data/interim/pyro-annotator/sequences/splits.json
uv run python scripts/add_data.py --src data/interim/pyro-annotator/sequences/fp \
  --type fp --splits-from data/interim/pyro-annotator/sequences/splits.json
dvc repro compute_fp_embeddings                              # freeze needs embeddings for new test FPs
uv run python scripts/freeze_test_selection.py               # append-only; git-diff shows the growth
dvc repro
```

One commit carries the coupled state: `import_plan.json`, `recurring_objects.json`,
both `registry.json` files and `sequential_test_lock.json`, plus `dvc push` for the
data. These files must travel together — splitting them across commits is how an
artefact ends up half-recorded.

The mental model: **plan and freeze are the two stateful, judgement-carrying,
git-committed commands; materialise and the builds are pure functions replayable by
`dvc repro`.** Plan owns what enters the dataset and in which split; freeze owns what
the test negatives are, forever.

## Invariants

Replacing the import design's invariant #2 ("annotator sequences never receive
`split: test`"), which is repealed:

1. **Test grows append-only.** Registry test entries are never removed (already the
   append-only rule); the lockfile never shrinks and never reorders. Every release's
   `sequential_test` is a byte-identical superset of the previous release's.
2. The FP half of the built `sequential_test` equals the lockfile exactly; the build
   performs no selection for test.
3. The lockfile is git-committed accumulated state, written only by
   `freeze_test_selection.py`, never a DVC output.
4. All sequences of one recurring object share one split — unchanged, now with test in
   range.
5. Annotator smoke alerts of one same-fire group (§6) share one split.
6. `n_fp == n_wf` per split in the built dataset — unchanged; for test it is enforced
   as `len(lockfile) == quota`.

## Verification

- **Bootstrap fidelity**: seeding from the built dataset reproduces its FP folder set
  exactly; a rebuild against the fresh lockfile is a no-op diff on `sequential_test`.
- **Freeze idempotency**: a second freeze with nothing new writes an identical file.
- **Append-only**: after an import adding test WF sequences, the new lockfile starts
  with the old one as a prefix; only additions follow.
- **Overflow**: with more annotator test FPs than open slots, pins stop at the quota
  and the surplus is still selectable later.
- **Stale lockfile**: the build errors when quota ≠ lockfile length, when a folder is
  unregistered or not `split: test`, and when a folder is missing on disk.
- **Leakage**: `tests/test_data_leakage.py`'s recurring-object assertion extends to
  test; existing folder/image overlap tests already cover test.
- **Same-fire**: unit tests for the transitive chaining, the window boundary, and
  split inheritance from previously planned folders.
- **Ingest**: `assignments_from_splits` accepts test; the old refusal test is inverted.

## Deferred

| Item | Why deferred |
|---|---|
| Append-only `yolo_test` FP selection | Accepted re-roll (Non-goals). The round-robin's full rounds are nearly stable; a lockfile there is mechanical once wanted. |
| Same-fire matching against the historical pool | Needs folder-name parsing across pools and a shared notion of camera identity; belongs with cross-pool recurring-object matching. |
| Keeping published metrics valid as-is (test-set versioning, `test_v1` reporting) | The comparability contract chosen here is re-evaluation on the grown test. Version-pinned reporting is a separate reporting-layer feature; the lockfile's git history already records every version's membership if it is ever wanted. |
| Growing test from *historical* pool data | The freeze command would support it (it selects from the whole pool), but deliberately only when new WF test sequences open slots. A policy for bulk-growing test is its own decision. |
